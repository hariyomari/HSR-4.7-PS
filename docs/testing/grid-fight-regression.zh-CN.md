# GridFight 回归

[English](grid-fight-regression.md) | 简体中文

`GridFightRegression` 基于当前资源缓存在内存中进行货币战争（GridFight）对局，检查服务端状态以及为客户端构造的消息。修改 `GameServer/Game/GridFight/` 下的任何内容、GridFight 请求处理器、GridFight 资源模型或对局存档后运行。

项目：[`scripts/GridFightRegression/`](../../scripts/GridFightRegression/)

## 运行方式

从仓库根目录执行：

```powershell
dotnet run --project scripts/GridFightRegression/GridFightRegression.csproj
dotnet run --project scripts/GridFightRegression/GridFightRegression.csproj -- --cache <Resource.bin>
```

- 不带选项时读取当前的 `Config/Resource.bin`。
- `--cache` 先把指定缓存复制到仓库内的 `tmp/GridFightRegression/Cache/`，再读取该副本。日志写入 `tmp/GridFightRegression/Logs`。

修改共享代码时还应构建整个解决方案：

```powershell
dotnet build March7thHoney.sln -c Release --no-restore
```

## 前提条件

- 带 GridFight 表的资源缓存。赛季由缓存中的 `GridFight_Season_ID` 决定，测试角色取自该赛季的角色池。
- 赛季专属检查只在匹配的缓存下运行：银狼/命运卜者选择队列和持续伤害契约只在赛季 1 运行；赛季 2 羁绊检查只在赛季 2 运行。缓存使用新版原生技能布局时，先运行 `BetaTableRegression`，再继续完整回归；旧版缓存仍执行原有的装备、宝钻、投资和选择队列测试。
- 回归不使用玩家数据库，也不写回资源缓存。测试状态和额外的测试装备只存在于进程内。最后的对局存档检查在系统临时目录新建 SQLite 数据库（`m7h-gridfight-regression-*`），结束后删除。
- **战斗 Buff 行。** `MazeBuffExcel` 还会加载 `GridFightTraitMazebuffS2.json` 和 `GridFightSpotLightMazebuff.json`（均为可选）。注册这两张表之前生成的缓存缺少黑洞引力和克拉拉模块使用的 93 条战斗 Buff 记录。可以把这类缓存离线升级到一个尚不存在的新文件：

  ```powershell
  dotnet run --project scripts/GridFightCacheUpgrade/GridFightCacheUpgrade.csproj -c Release -- Config/Resource.bin <资源目录> <新输出文件>
  ```

  升级工具会重新读取输出，并核对除新增 Buff 行之外的内容没有变化。复制到 `Config/Resource.bin` 之前先用 `--cache <新输出文件>` 运行回归，并备份原缓存；回滚时同时恢复程序和缓存。
- **生成缓存。** 用旧缓存补齐缺失的表和行时，GridFight 表一律以新 dump 为准，不从旧缓存补行（旧缓存中有 14 条赛季 1 词缀，不能混入）。4.6.52 的 `PetConfig.json` 字段名被混淆，生成该缓存时使用了 4.6.51 版本。参见[从客户端导出重建资源缓存](../operations/resource-cache-from-client-export.zh-CN.md)。

## 覆盖范围

### 对局核心流程

- 全部可选传送门开局及其 protobuf 往返；装备追踪；宝钻；骰子；选择队列；20 场战斗的完整路线；周期奖励；重复请求；中止结算。
- 传送门与契约、投资奖励、银河学者、命运卜者、银狼升级选择、装备与羁绊追踪、商店锁定及相关同步消息。
- 自动穿戴统一检查装备锁定、穿戴条件与槽位；显式目标无效时不转移到其他角色。
- 装备追踪的批量更新先验证再提交；完成状态由实际穿戴推导，客户端伪造或残留的状态不会影响自动穿戴。
- NPC 装备在创建时即锁定，不会先被追踪系统穿到玩家角色身上。
- 手动与自动宝钻合成使用同一套配方；保留满星角色和切换形态的商店过滤；处理候选池为空的情况。
- 保留骰子绑定与战后重随；同步临时装备的删除；禁止单独转移临时装备；出售或合成角色时回收临时装备。
- 装备按备战阶段产金；重复的备战请求不重复发奖。
- 银狼、命运卜者的选择逐个发布，不会占用同一个队列位置；选择期间禁止移动、出售目标角色或进入战斗。
- 周期性投资接入节点回调；黄金期货触发后重置间隔计数。
- 处理器使用当前的 `CmdIds` 常量。

### 赛季与赛季隔离

4.6.51（4.7 测试服）资源把 `GridFight_Season_ID` 改为 2，赛季 1 和赛季 2 的行同表共存：`GridFightRoleBasicInfo`（赛季 2 角色编号为头像 ID × 100 + 2，另有成本档变体）、`GridFightTraitBasicInfo`、`GridFightEquipment` / `Consumables` / `Forge`、`GridFightCraftConfig`（同一对基础装备在两季合成出不同物品，如 350201+350201 → 35030101 / 47030101）。`GridFightSeasonTalent` 则把同一批 ID（2011–4061）用作赛季 2 的天赋。

- 加载 `GridFightSeasonItem.json`、`GridFightSeasonCraft.json`（物品/合成 → 赛季），由 `GridFightSeasonScope` 统一判定；没有这两张表的旧缓存视为全部共享。
- 商店、开局、补给、宝珠与奖励（随机角色、随机装备、指定角色）、锻造、骰子、合成、图鉴只取当前赛季内容。`SpecificAvatar` 与 `101000+ID` 角色宝珠按头像 ID 解析为当前赛季的角色。
- 4.6.51 去掉了 `GridFightCamp.SeasonID` 与 `RoleBasicInfo.RoleSavedValueList`：没有赛季的阵营视为共享；缺少 SavedValue 列时，角色池改用赛季 2 规则（排除 `IsFakeAvatar` 与阿哈 151112/151122/151132 成本档，七费档按 `ShopPrice` 第 7 行定价）。
- 赛季 1 专属机制只在赛季 1 生效：昔涟/银狼 LV999 校验、受限角色种子、4.5 商店稀有度表、赛季天赋 2011 的终局回合治疗及 3560xxxx 天赋战斗 buff、天赋 4032 的宝珠奖励（`GridFightRewardRules.json` 的 `SeasonIds`）。
- `GridFightFormationWave` 新增一条省略 ID（0）的 5 人波次，战斗仍使用编号 5 的波次。
- 赛季 2 每局随机一名伙伴（`GridFightPetPal.json`，跳过无效果的 1 号）及其一条效果，经 `GridFightGameInfo` 的伙伴同步（字段 1984，条目字段 9 为伙伴、8 为效果）和结算 `GridFightFinishInfo`（字段 1836）下发。客户端开局流程直接读取第一条伙伴效果，缺失时空引用会导致“开始对局”没有反应。
- 对局结算（胜利或退出结算）推进 `GridFightFinishGamePlay` 任务，参数 1 为标准博弈、2 为超频博弈；超频博弈由 `GridFight_OC_UnlockQuest`（7302115）解锁。
- 地图控制台（`Prop_Common_GridFightConsole_01`）按 `ByCompareMainMissionState(8037100)` 分支，省略的状态取类默认值 `Finish`：`GridFight_Tutorial_Main_Mission_Id` 已完成时打开新入口，否则打开赛季 1 的旧页面。服务端如实下发该任务状态，相关覆盖见 `LoginSceneRegression`。
- 标准路线按赛季选取：`GridFightStageRoute` 没有赛季列，赛季 N 的段位路线编号从 N×1000 起（赛季 1 为 1000–1800、1801，23 个节点；赛季 2 为 2000–2800、2801，16 个节点），1000 以下为教程/首玩路线。
- 4.6.51 客户端只用 `GridFightLevelInfo` 字段 12 下发的路线节点构建关卡节点（章节 5、小节 1；参数中 2 为关卡、7 为惩罚规则、8 为增益节点、12 为基础金币、14 为节点类型）。缺失时当前节点为空，进度条显示 0-0，备战页无法出战。
- 赛季 2 路线中补给节点之后可能紧接精英分支；补给回合开始后进入精英遭遇选择。
- 消耗品增删同步必须带嵌套的 `GridFightConsumableInfo`（`GridFightConsumableUpdateInfo` 字段 13），客户端只读该字段。
- 赛季 2 等级表新增只能由效果达到的 11 级。普通经验（购买、战斗）只升到 `GridFight_DefaultPlayerLevelMax`（10）；10 级没有升级经验，不能滚入 11 级。
- 补给卡片（`GridFightSupplyRoleInfo`）必须在字段 13 带角色掉落（`GridFightDropEntry`，角色/1 星），装备放在字段 6 的掉落列表。客户端 `GridFightDraftItemData.Create` 无条件读取字段 13，缺失时空引用，表现为卡在补给节点（如 1-3）的结算。
- 赛季隔离检查覆盖：角色池、传送门与投资池、商店 300 次刷新、补给、全部可解析宝珠各开启 8 次、锻造、随机装备、合成、图鉴、骰子填充，以及完整路线中出现的角色、装备和报价。

协议结构来自 4.6.51 客户端反汇编，不是抓包。客户端不包含的规则（商品池、触发节点、阈值）按羁绊描述实现，并在代码中注明为推测。不在 `Resource.bin` 中的表（模板装备、白厄薪火、克拉拉改装、奇美拉、开拓商店、翡翠黑市、欢愉模板）由仓库外的脚本生成为 `GridFightSeasonTwoTables.cs`。

### 投资策略与投资环境

投资策略即 augment，投资环境即传送门（portal）。

- 传送门只允许 1 次免费刷新：待选信息的 `free_reroll_count` 固定为 1，`reroll_count` 记录已用次数（与投资待选一致）；第二次刷新返回失败，候选不变。
- 已被刷掉的投资不会回到同一次选择的其他槽位。
- 补给回合开始后按通用规则进入下一节点（精英遭遇、投资、黄金期货、补给），而不只判断精英分支；补给后到期的黄金期货此前会被推迟。
- 剩余投资不足一次报价时，投资品质抽取返回 `None`，投资节点直接返回备战，不再抛出异常。
- 好运令牌·银（130901）在第 3 个节点发放的 350107 是 `GridFightConsumables` 消耗品，按消耗品发放并经 `UpdateGridFightConsumableList` 同步（此前按装备发放，因表中不存在而静默失败）。
- 局外效果（`GridFightAugmentEffects.cs`、`GridFightPortalEffects.cs`）的依据是：4.6.51 `GridFightAugment` / `GridFightPortalBuff` 的 `HexDesc` / `PortalBuffDesc` 哈希在 4.6.0 正式服 TextMapCHS 中命中的描述（命中即文字未改），数值取 4.6.51 的 `EffectParamList`：
  - 获得时奖励（金币、经验、免费刷新、小队生命与上限、随机 N 费/指定星级角色、随机简易/进阶/光辉装备、随机星徽、指定道具与武装箱）逐条发放；单条失败（如备战席已满）只跳过该条，已发放的照常同步。
  - 节点触发：每次进入节点、经过 N 个节点后、接下来 N 个节点、每 N 个节点、进入首领节点、首领战后、位面开始。
  - 免费刷新由服务端计数，优先于金币消耗；有免费次数时商店 `refresh_cost` 下发 0（协议没有单独的免费刷新字段）。
  - 投资环境：红钻/蓝钻贵族、战力提升、战力飙升（属性成长除外）、人才储备开局角色、特权阶级、二手市场、长线利好、彩虹/黄金/白银时代、头彩/尾彩、成功经验、策略大师（额外投资选择除外）。
- 赛季 2 投资（`GridFightSeasonTwoAugmentEffects.cs`）没有公开文本，描述取自游戏内的投资策略图鉴，按图鉴顺序和 `EffectParamList` 与 `GridFightAugment` 行对应。
- OSBETAWin4.7.51 的赛季 2 投资列表由 307 项变为 298 项。103601、204001、204101、304001、304101、304201、304301 只保留在赛季 1 列表中，效果配置保留；212001、312001（`355100600` 星徽套组）整行删除，已从 `EmblemSetAugments` 移除。效果表两个赛季共用，因此回归断言每个已配置的投资都在某个赛季的投资列表里，并且投资只从当前赛季的列表发出。
- 邀请函传送门 2101–2119 发放对应羁绊的星徽；4.7.51 中其参数由星徽组号改为星徽物品 ID，解析结果不变。概念股传送门 2201–2214 实现于 `GridFightConceptStockPortal.cs`。
- 4.7.51 新增的赛季 2 传送门 149–152 和 1015 进入传送门池，并通过开局与消息往返检查。
- 经济策略（`EconomyEffectsRegression`），以真实结算、成功/失败消费、免费刷新、额外投资选择及其刷新次数、购买消息、角色战斗字段、奖励回滚和旧存档恢复检查：

### 同步顺序

人才大礼包、晶矿、阿哈商品等一次发放多名角色时，后发的角色可能落在同一次发放中前一次合成刚空出的备战格。原先的同步先下发全部 `AddRoleInfo` 再下发合成，客户端收到时该格仍被占用：格子显示为空，服务端却仍有角色，拖入即返回“消息获取失败”。现在每个获取结果的新角色紧接其合成之后下发；赛季 2 的后续同步此前完全不下发获取结果的合成步骤，现已补上。`AppendRewardApplication` 的属性刷新也不再提前更新本次奖励中尚未下发的角色。`SyncOrderRegression` 以客户端棋盘模型按顺序回放同步，旧顺序会报 “role added on taken cell”。

### 对局存档与退出

- 进行中的对局以快照（`GridFightRunSnapshot`，MemoryPack，Base64）存入 `GridFight` 表的 `RunInstance`，下一局编号存于 `NextSessionUniqueId`。该表在启动时自动创建，重置账号时随其他玩法数据删除。
- 保存时机：每个币战请求结束时（`GridFightHandler<T>`，失败也保存）、战斗结算、`QuitBattleCsReq`、`/grid` 指令和下线；登录时由 `GridFightManager` 恢复。快照与当前赛季不符、引用的角色或怪物已不在资源中或无法解析时，丢弃该局并记录警告，不影响登录。这包括棋盘、备战席角色或商店卡的角色不在已加载角色表中的情况（例如在 4.6.52 缓存下存有 `151102` 的对局）。
- 恢复时对局仍处于战斗中（断线或重启时战斗未结算），按 `BATTLE_END_QUIT` 结算为失败：连胜清零、战斗计数 +1，不发金币和经验，不推进路线。客户端随后通过 GetData 取得解锁后的完整状态。
- `QuitBattleCsReq` 清除币战战斗时同样按失败结算并下发解锁同步（与 `PVEBattleResultCsReq` 的 `BATTLE_END_QUIT` 一致）；此前对局会卡在战斗阶段，再也无法出战。在已观察到的客户端日志中，退出都走 `PVEBattleResultCsReq`，从未发送过 `QuitBattleCsReq`。
- 撤退：`BATTLE_END_QUIT` 之后官方客户端立即发送 `GridFightQuitLeaveGamePlayCsReq` 回到大世界。服务端仍按失败结算（无免费重打），但只下发解锁同步，不再下发结算页、路线同步和结算通知，避免黑屏；客户端重进时通过 GetData 取得结果。
- 快照只追加成员，不重排或删除。会话中 15 个仅用于下一次同步的通知缓冲（`GridFightSession.PersistenceTransientFields`）不保存，其状态变化已写入其他字段。
- 检查：逐个字段写入样本值后保存/恢复比对（新增字段若未映射会失败）；完整路线每一步的保存/恢复比对（包括共享对象，如所选遭遇与当前战斗计划为同一实例）；在每一步恢复后的副本上打完整路线；拒绝其他赛季的快照；以及在临时 SQLite 上的重新登录、重启后恢复并结算未完成的战斗、离开对局清除存档、丢弃损坏的存档。
